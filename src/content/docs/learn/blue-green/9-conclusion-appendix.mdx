## উপসংহার

Application deployment-এর সাথে ঝুঁকি জড়িত — human error, process ত্রুটি, downtime, rollback-অক্ষমতা। Cloud computing, deployment ও automation framework আর blue/green-এর মতো নতুন কৌশল এই ঝুঁকি কমায়। AWS-এর **utility billing** মডেল আর বিস্তৃত automation tool-এর কারণে scale-এ **দ্রুত ও সাশ্রয়ীভাবে** blue/green চালানো আগের চেয়ে সহজ।

দলিলের তথ্য: প্রথম প্রকাশ ১ জুন ২০১৫; ২১ সেপ্টেম্বর ২০২১-এ technical accuracy-র জন্য হালনাগাদ।

## সারণি থেকে মনে রাখার মতো

- **DNS-নির্ভর সব প্যাটার্নে** rollback-ঝুঁকি **XXX** — একটাই কারণ: DNS TTL।
- **Rollback-এ সবচেয়ে নিরাপদ দুটো**: Swap ASG behind ELB আর launch configuration আপডেট — দুটোতেই rollback **X**, কারণ DNS জটিলতা নেই।
- **সবচেয়ে কম অটোমেশন-নির্ভর**: OpsWorks clone — people/process ঝুঁকি X, auto-healing capability-র সুবাদে।
- **Cost-এ একমাত্র XXX**: OpsWorks — দুই পূর্ণ stack সমান্তরালে চলে।
- **Launch config প্যাটার্নের দুর্বলতা অন্য জায়গায়**: heterogeneous fleet-এ ত্রুটি শনাক্তকরণ (application issues **XXX**)।

## Exam traps

- "দ্রুত rollback" চাইলে **DNS-ভিত্তিক প্যাটার্ন বাদ** — উত্তর Swap ASG behind ELB বা launch config আপডেট।
- "দুই পূর্ণ পরিবেশ সমান্তরালে চলে" জাতীয় বর্ণনা = **OpsWorks clone** — cost-ঝুঁকি XXX।
- Beanstalk-এ "canary সুবিধা থাকলেও production traffic-এ canary নয়" — performance-ঝুঁকি XXX (**full cutover**)।
- Heterogeneous fleet-এ ত্রুটি-শনাক্তকরণ কঠিন — এটা **launch configuration** প্যাটার্নের application-issues ঝুঁকি XXX-এর কারণ।
